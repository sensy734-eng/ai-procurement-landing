# 采购管理系统 数据库脚本说明

本目录为第二步交付物，含 49 张表的完整 DDL 与初始化数据脚本。全部脚本已在 MariaDB 10.4.32 上实测执行通过，校验脚本 12 项全部符合预期。

## 一、文件清单与执行顺序

按文件名前缀顺序执行，00 会重建数据库。

    00_create_database.sql      创建数据库，会先删除同名库，仅初始化与重置时执行
    01_schema_a_base.sql        A 基础数据 13 张表
    02_schema_b_bill.sql        B 采购单据 10 张表
    03_schema_c_stock.sql       C 库存 2 张表
    04_schema_d_approval.sql    D 审批 2 张表
    05_schema_e_price.sql       E 价格 3 张表
    06_schema_f_platform.sql    F 平台权限 8 张表（含 sys_session）
    07_schema_g_kb.sql          G 知识库 5 张表
    08_schema_h_ai.sql          H 智能助手 6 张表
    10_init_dict.sql            字典类型与字典项，含部门树
    11_init_platform.sql        四角色、156 个权限点、授权、用户、数据范围、审批节点
    12_init_ai.sql              系统参数、五类意图、参数规格、实体别名
    13_init_demo.sql            演示主数据与演示单据
    14_init_kb_demo.sql         演示知识文档与切块

命令行执行方式（以本机路径为例，其他环境替换 mysql 客户端路径即可）：

    cd db
    mysql -u root -p --default-character-set=utf8mb4 < 00_create_database.sql
    mysql -u root -p --default-character-set=utf8mb4 < 01_schema_a_base.sql
    ...依次执行至 14_init_kb_demo.sql
    mysql -u root -p --default-character-set=utf8mb4 -t < 99_verify.sql

脚本内无绝对路径、无主机名、无账号密码，换机器只需改命令行参数。

## 二、表清单核对

按域统计：A 13、B 10、C 2、D 2、E 3、F 8、G 5、H 6，合计 49，与规划书 5.2 正文一致。

规划书 5.2 的表清单实际列到 48 个表名，缺口为会话表。本设计补 sys_session，承担 M11-1-1 建立会话、M11-1-2 会话保持与超时、M11-1-3 退出登录三处功能点，表数由此达到 49。这一条在第一步已与你确认。

## 三、三处口径冲突的裁决

规划书内部有四处字段级不一致，直接照抄会写出自相矛盾的表。以下是我的处理，需要你确认，尤其第一条。

### 3.1 已交付数量的写入点

冲突点：5.3.4 写 delivered_qty 由交付进度登记累加，5.3.6 写入库确认回写订单明细的已交付数量。两处若都实现，同一批货会被累加两次。

裁决：delivered_qty 只由入库单确认写入，与库存数量的唯一写入点同构。delivery_progress 表保留，仅作交付过程记录与跟单查询，不参与履约状态判定。理由是这样不会出现已登记交付但未入库、订单却显示部分交付的漂移，而且与 R2 的单一写入点纪律一致。

影响：交付进度登记的动作不会立刻改变订单履约状态，变成入库确认才改变。演示数据中订单 1 的 600 已交付，就是入库确认的结果，交付登记表里有同一条记录，两处数量一致但不互相累加。

### 3.2 驳回后的生命周期状态

冲突点：5.3.1 只给生命周期状态五个值，没有已驳回；M2-3-3 却写已提交到已驳回的状态变化。若把已驳回塞进生命周期枚举，三状态就退化成两状态。

裁决：驳回时审批结果状态置 3，生命周期状态回落为 1 草稿。界面上以审批结果状态为 3 显示已驳回，可编辑也据此判断。这样已驳回是两字段的组合，不是第三个状态值。

影响：演示数据中申请单 CG-SQ-20261014-0001 就是这一组合，生命周期 1 加审批结果 3，可作为论文举例。

### 3.3 价格版本号与乐观锁同名

冲突点：5.3.10 的参考价表有一个 version 字段表示价格历史版本，而 5.1 规定每张表都有 version 作为乐观锁版本号。

裁决：参考价的业务版本改名为 price_version，公共字段 version 保留给乐观锁。知识文档同样处理，文档版本仍叫 version，乐观锁改名为 version_lock，因为 doc_name 与 version 属于业务语义，不适合改名。

## 四、四处字段补齐

以下字段 5.3 的字段表未列，但所属功能点要求，缺了就无法实现。

1. purchase_request_item 增加 est_price 与 est_amount。5.3.1 主表有 total_amount，M2-2-2 要求编辑明细后重算单据金额，但 5.3.2 明细没有单价，金额无从计算。est_price 允许为空，用于预估金额，不参与订单定价。
2. purchase_order 增加 buyer_id 与 dept_id。M3-1-1 要求按数据范围过滤，采购员的范围是本部门单据，没有这两个字段无法注入过滤条件。
3. purchase_order_item 增加 source_request_item_id。5.5 说明申请行与订单行是多对多转单关系，按行转订单后要能追溯来源行。
4. purchase_order 增加 total_qty，purchase_order_item 增加 item_no、order_item_id 一类冗余键，用于列表展示与不联表查询。

## 五、两处结构选择

1. 部门用字典项表达。表清单没有部门表，但 sys_user.dept_id 与数据范围授权表的数据范围维度都需要部门数据。用 dict_type 中 type_code 为 dept 的一组 dict_item 表达，parent_id 形成两级树，以此守住 49 张表的表数。若后续要做部门主管、部门级权限继承，再单独立表。
2. 公共库存的归属标识存 0 与 PUBLIC，不存 NULL。因为 MySQL 唯一键对 NULL 不做约束，若 owner_id 允许为空，库存余额的六元组唯一性会失效，并发下会写出两条相同余额。

## 六、权限点与角色授权

权限点共 156 个，编码格式为模块:对象:动作三级固定，按动作拆而不按菜单拆。分布：M1 30、M2 20、M3 27、M4 8、M5 17、M6 7、M7 3、M8 2、M9 2、M10 11、M11 22、M12 7。

智能模块（M7、M8、M9）共 7 个权限点，动作只有 query、list、view 三类只读，校验脚本第 4 项专门检查违规数为 0。

角色授权数：采购员 80、采购主管 63、仓管员 36、系统管理员 64。四条边界要留意：

1. 系统管理员只有反审一个业务动作（m3:order:reaudit），不持有任何审批权，避免配置者即审批者。
2. 采购主管持有审批、驳回、整单关闭、订单作废、按行退回、按行关闭、让步接收，这些各自独立成点，答辩时可现场演示谁能做什么。
3. 仓管员持有验收与入库全流程，但不含让步接收与入库单作废，这两个动作归主管。
4. 采购员不含任何审批与关闭动作。
