## 三、全流程演示链（轮次 12）

这条链的价值在于：模块级冒烟全绿并不等于整链通——验收合格数没带进入库单、
确认入库没回写已交付，单模块都测不出来。

| 步骤 | 动作 | 关键断言 |
|---|---|---|
| 1 | 采购员建申请（两行）→ 提交 → 主管或签 | 提交后生命周期 2 / 审批中；通过后 3 / 2 |
| 2 | 申请转订单 → 提交 → 双人会签 | 同供应商两行合并一张单；会签未齐仍在审批中；转单后申请行「已转完」 |
| 3 | 仓管员到货登记（行1 全合格 100，行2 到 50 含 10 不合格）→ 验收提交 | 逐行守恒；整单结果由明细重算为不合格；可入库量只算合格 = 140 |
| 4 | 按合格量生成入库单 → 补登库位 → 确认入库 | 入库明细只含合格量 [100, 40]；草稿库位为空；确认后库存 +100 |
| 5 | 订单回写 | 行1 已交付 100、行2 已交付 40（不合格 10 不回写）；整单履约变部分交付 |
| 6 | 看板核对 | 订单 +1；部分交付桶 +1；趋势总额 +2750；该供应商排名与汇总各 +2750；汇总按状态恰好一条组合 +1 |
| 7 | 智能助手 | 按单号查到新单，答案含单号与状态；查询审计落库 |
| 8 | 只读约束 | 看板与助手查询前后订单总数、库存数量不变 |

## 六、测试数据从何而来

测试数据分六层，前三层是长期基线，后三层按需生成或跑完即清。

| 层 | 脚本 | 内容 | 规模 | 生命周期 |
|---|---|---|---|---|
| ① 字典 | `db/10_init_dict.sql` | 计量单位、物料类型、供应商类型、部门、结算方式等字典项 | 69 项 | 长期 |

| ③ 主数据与演示单据 | `db/13_init_demo.sql` | 8 物料、4 供应商、3 申请单（已审核/草稿/被驳回）、2 订单（部分交付/草稿含 6.98% 偏离）、1 验收单、1 已确认入库单、库存 600、4 参考价、4 快照 | 见左 | **所有冒烟的公共基线** |
| ④ 知识与 AI 种子 | `db/14_init_kb_demo.sql`、`db/12_init_ai.sql` | 2 篇制度文档（10 切块）、5 类意图、意图参数规格、实体别名 | — | 长期（向量与索引由程序生成） |
| ⑤ 运营演示 | `db/24_init_ops_demo.sql` | 7 张历史订单覆盖五个状态桶、2 张入库单、9 行库存与流水、2 条待处理会签、4 个缺口物料 | 9 单 / 10 行库存 | 可被 `26_revert` 撤销 |
| ⑥ 冒烟自造 | 各冒烟脚本运行时 | `smk`/`smoke` 前缀 + 时间戳的申请、订单、验收、入库 | 每轮数条 | 跑完由 `15~27_clean` 清掉 |

三条纪律：

1. **演示数据与冒烟基线分开**：`13` 是公共基线，`24` 是给页面看的运营数据。混在一起会让轮次 7
   那类按干净基线写死的断言（预警 5 种、对账 5 个键）在无关模块上失败，所以补了 `26_revert` 用于撤销。
2. **自造数据必须可清除**：单号带时间戳避免撞唯一键，清理脚本按前缀 + `source_request_id` 关联删除
   （转单生成的订单 remark 不带前缀，只按备注删会留孤儿单）。
3. **全部为自造数据**：企业名、人名、单号均为虚构，`13_init_demo.sql` 与 `14_init_kb_demo.sql`
   头部都有声明，不对应任何真实公司或人员。

## 七、复跑方法

顺序不能乱：`clean` 脚本只删自己那轮的数据，`24` 造演示数据、`26` 撤演示数据，
`22_clean` 会清空知识库派生索引（轮次 10 冒烟开头会自己重建）。

```bash
# 0) 前置：后端 8080、前端 5173、MariaDB 在线
# 1) 回归链（每步都要带库名）
mysql -uroot procurement_db < db/26_revert_ops_demo.sql   # 撤销运营演示数据
mysql -uroot procurement_db < db/16_clean_smoke_round3.sql && python scripts/smoke_round4.py
mysql -uroot procurement_db < db/17_clean_smoke_round4.sql && python scripts/smoke_round5.py
mysql -uroot procurement_db < db/18_clean_smoke_round5.sql && python scripts/smoke_round6.py
mysql -uroot procurement_db < db/19_clean_smoke_round6.sql && python scripts/smoke_round7.py
mysql -uroot procurement_db < db/20_clean_smoke_round7.sql && python scripts/smoke_round8.py
mysql -uroot procurement_db < db/21_clean_smoke_round8.sql && python scripts/smoke_round9.py
mysql -uroot procurement_db < db/22_clean_smoke_round9.sql
mysql -uroot procurement_db < db/23_clean_smoke_round10.sql && python scripts/smoke_round10.py
# 2) 演示数据 → 看板与全流程
mysql -uroot procurement_db < db/24_init_ops_demo.sql
python scripts/smoke_round11.py
python scripts/smoke_round12.py
mysql -uroot procurement_db < db/27_clean_smoke_round12.sql
mysql -uroot procurement_db < db/25_clean_smoke_round11.sql
# 3) 收尾校验与界面
mysql -uroot procurement_db -t < db/99_verify.sql
python scripts/gen_api_list.py --check
cd web && node scripts/ui_smoke.mjs
```

轮次 1~3 的复跑更简单：`15_clean_smoke.sql` → `smoke_round1.py` → `smoke_round2.py`
→ `16_clean_smoke_round3.sql` → `smoke_round3.py`。

## 八、已知局限（如实记录，不修饰）

1. **M8 拒答的边界**：问句含「采购」「制度」这类通用词时，词元命中容易 ≥2，可能把无依据的问题
   答成「目的与适用范围」。改进方向是词元命中按 idf 加权或建通用词降权，等拒答率数据再定。
2. **M12 图表无交互**：SVG 自绘，没有缩放、联动、图例点选。若答辩要现场「点图钻取」，
   需先定交互口径再评估引入图表库。
3. **未做压力与并发测试**：只覆盖了「并发提交只成功一次」这类功能级并发断言（轮次 4），
   没有做吞吐量、响应时间与连接池压测，论文第 7 章如需性能数据要另做实验。
4. **单机单库实测**：MariaDB 10.4.32 单实例、无主从、无缓存层；数据量在千行级，
   所有性能判断都不具备横向扩展意义。
5. **规则式「模型」而非真模型**：M7/M8/M9 一版是规则 + 模板转述（规划书风险项预留的降级路线），
   意图准确率与引用覆盖率的数字是规则口径，接真模型后需重测并做对照实验。
6. **浏览器覆盖只有 Chrome**：界面走查用系统 Chrome 无头模式，未验证 Firefox/Safari/移动端。
