# AI 功能演进建议：从查询入口到业务任务协助

状态：订单审查与需求起草已在本地实现，真实模型质量待配置凭据后验证。日期：2026-11-09。实际入口、数据、边界与验证见[任务助手实现说明](ai-task-assistants.md)。本文保留演进思路，通用聊天追问等未列为已实现的建议仍属后续工作。

目标：以采购为可复现业务场景，展示发现业务摩擦、选择适合 AI 的环节、复用已有系统、处理不确定性并验证效果的能力。方案沿用 Java/Vue、现有模型网关与权限体系。

## 1. 基于当前代码的判断

- `DataQueryExecutor` 已支持订单状态、交付进度、历史价格、可用库存和供应商交付五类受控查询。
- `AiChatService` 目前按知识/教程或数据查询分流，每次主要处理一个任务；`ChatRequest` 尚无来自业务页面的显式对象上下文。
- `OrderVO` 已提供订单明细、审批历史、变更历史和交付记录；价格模块已有参考价、偏离和历史成交证据，适合组合为审查任务。
- 采购申请已有主表、明细行、物料及归属对象选择，适合接收结构化候选内容。
- 原始88题在当前离线配置下尚未全部通过，且存在旧 fixture、权限期望和路由问题。不能把该成绩直接作为新功能的模型准确率，也不能跳过真实模型验收。

当前最大的新增价值是：让 AI 理解用户正在处理的对象，组合授权范围内的数据与制度证据，并交付可以核对和继续操作的结果。

## 2. 优先级

| 顺序 | 功能 | 用户解决什么问题 | 可展示的工程贡献 |
|---|---|---|---|
| P0 | 现有查询稳定化与页面上下文 | 少复制单号，正确理解追问、日期与歧义 | 上下文建模、结构化理解、权限继承与真实模型评测 |
| P1 | 订单审查助手 | 审查一张订单时跨页面找证据、对照制度 | 多来源证据组合、受控工具调用、规则与生成分工 |
| P2 | 采购需求起草 | 将口头需求重复录入多行表单 | 信息抽取、实体消歧、多轮补全、人工确认与原表单集成 |
| 后续 | 报价单解析与比价 | 从 PDF/图片手工提取和核对报价 | 文档解析、字段溯源、单位/税价口径校验；需要新增专门语料 |
| 后续 | 业务简报 | 将已有统计结果组织成可阅读的摘要 | 可复用证据体系，但初期优先级低于具体任务协助 |

本轮按用户授权完成 P1 + P2，以订单详情上下文和申请表集成形成任务流程。P0通用聊天追问另行迭代，真实模型与效率对照以实际结果为准。

## 3. P0：把已有能力做成稳定、自然的使用体验

在订单详情增加“AI 协助”入口，显式显示当前订单。前端仅传对象类型、ID和页面版本；后端重新读取对象并验证权限，浏览器传来的部门、金额和角色都不成为可信事实。

对话支持“这张单”“它的交付情况”等指代。切换对象、切换角色、权限变化时使旧上下文失效。当前页面对象与聊天中明确提到的另一个对象冲突时，先让用户确认。

把有效物料、时间范围、筛选条件显示为可修改的条件卡。缺失条件和多个同名物料采用明确选项澄清；“还没交完”和“已经逾期”分别处理。

模型运行状态和实际执行路径保持可辨别。可展示“读取订单”“核对价格”“检索制度”等实际执行阶段，不展示或编造模型内部思考。经过校验的最终回答才显示为结论。

知识问答先补齐同义问句、追问、无答案、版本冲突和条件/例外完整性评测。现有数值守卫无法替代这些语义评测。原冻结保留集继续不用于调参。

## 4. P1：订单审查助手——推荐的主展示功能

### 使用场景

采购主管打开一张订单，提出：“帮我检查这张订单的价格和交付情况，有哪些需要核实的事项？”

系统交付一张审查卡，包含：

1. **已核实事实**：订单状态、明细、交期、已交付数量和可访问的价格证据，提供原记录入口与读取时间。
2. **规则检查结果**：按系统现有口径计算的价格偏离、逾期或资料缺失。未取到某项证据时标为“未检查”，不能视为正常。
3. **AI 解读**：针对本次问题组织事实与关联条款，区分已知事实和待核实事项。
4. **依据**：逐项链接订单行、交付记录、统计范围或制度原文。
5. **建议处理入口**：查看相应明细、补充资料或打开已有业务页面。AI 不代替审批、不自动联系供应商。

例如，系统可以确认“交期已过且尚未交付完整”，但如果没有相关记录，就不能把原因写成“供应商产能不足”。价格偏离也不能直接推断为不合理采购或欺诈。

### AI 的实际职责

模型理解用户关注的是价格、交付还是流程，并将多来源证据组织成针对问题的解释和待核实清单。金额、比例、日期差、状态转换与规则阈值由现有 Java 逻辑计算，模型不能重算后覆盖这些值。

首版限定为单张订单，采用有界工作流：确认对象 → 取得授权数据 → 运行确定性检查 → 检索相关制度 → 生成有证据的解释 → 校验输出。根据问题选择有限的检查分支，工具次数、结果大小和总时长均有预算。

### 实现落点

- 页面：在订单详情增加侧栏，复用现有 AI 结果卡中的引用、降级与跳转组件。
- 服务：增加订单审查编排服务，复用 `LlmGateway`、订单详情和受控查询服务；业务校验规则只保留一份来源。
- 工具：显式登记订单、交付、价格证据和知识检索等只读能力，限定输入输出结构。避免把全部 Spring 服务自动暴露给模型。
- 权限：每次工具调用都检查功能权限和对象数据范围。现有部分权限位于 Controller 注解，直接调用 Service 不会自动获得该保护；价格证据和跨部门统计尤其需要补齐范围约束。历史均价及来源单号只能来自当前账号允许访问的记录，不能把全局快照直接包装为个人可见证据。
- 证据：由服务端生成证据 ID，记录对象/字段、版本或内容哈希、读取时间和统计口径。模型仅能引用本轮实际提供的证据。
- 一致性：业务数据读取完成后结束数据库事务，再调用模型；结果标明快照时间，返回时发现关键对象变化则标记过期或要求重跑。模型调用期间不持有业务行锁。
- 降级：模型失败时保留真实数据和确定性检查结果，明确标注“未生成 AI 解读”；制度仅展示参考原文。不得用模板结论冒充生成结果。

建议新增独立任务结果结构，包含 `facts`、`checks`、`interpretation`、`evidence`、`missingEvidence`、`actions`、`asOf` 和运行信息。兼容已有问答响应，不把审查任务硬塞进现有 `answerMode` 的知识问答语义。

### 验收场景

正常订单、价格偏离、部分交付、逾期、无参考价、无历史样本、制度缺失、越权订单、受限统计、模型失败、上下文被注入指令、生成期间单据变化。

核对规则事实、证据对应关系、无依据断言、正确暴露缺口和权限隔离。先建立人工可核对的 fixture，再对真实模型重复运行，记录每项输出和执行路径。

## 5. P2：采购需求起草——展示从语言到操作的落地

### 使用场景

用户输入：“维修项目需要200个螺栓，下周五之前用，帮我准备申请。”

AI 抽取物料描述、数量、需求日期与归属对象；查询可用档案后，对于多种规格或多个项目给出候选。缺失的必填信息逐项询问。最终生成可编辑的候选表格，用户点击“填入申请表”后再通过原页面保存。

### 边界与数据流

- 模型只输出候选内容，物料和项目 ID 由后端按授权档案确认，不能直接采信模型编造的 ID。
- 单位来自物料档案；用户单位不匹配时询问，不推测“箱”与“个”的换算。
- 相对日期根据服务端日期和时区展开，并显示具体日期供确认。
- 预估单价、建议供应商等用户未提供的内容保留为空；如提供历史参考，必须标明来源并由用户选择。
- 展示字段来源：用户原话、档案确认、待确认。提供原话到字段的对应关系和覆盖前后差异。
- 第一版只填充前端未保存表单，不触发创建、提交或审批接口；保存沿用业务权限和校验。应用建议不得覆盖用户已有编辑，冲突时保留选择权。
- 采用独立起草入口和受限接口，保留现有聊天对业务写入的拒绝边界。技术会话/审计记录与业务写入分别定义。
- 现有申请主表与明细行分别维护，接入时分别检查创建权限和行维护权限。自动整单保存若在未来开放，需要额外设计事务、幂等与明确确认，不能混入本阶段。

模型负责非结构化需求理解、字段抽取和补全对话；业务服务负责档案解析、单位和权限校验；用户负责最后确认与业务提交。

### 验收场景

多行需求、同名物料、规格缺失、未知项目、数量或单位歧义、相对日期、没有价格、模型虚构编号、越权归属对象、模型失败、重复应用、表单已有编辑。

以字段准确率、正确澄清率、草稿可用率和应用后人工修改量评估。对比人工录入时固定同一批任务，并交换执行顺序以减少熟练度影响。小样本演示结果不外推为生产效率。

## 6. 如何证明 AI 改造有效

| 需要证明的能力 | 对照方式 | 报告内容 |
|---|---|---|
| 语言理解 | 规则路径与真实模型处理同一批问句 | 意图/字段准确率、澄清与拒答、实际模型接管情况 |
| 订单审查 | 业务页面及确定性检查，与相同证据上的 AI 协助任务对照 | 任务完成率、查证用时、事实错误、证据覆盖、缺口是否正确暴露 |
| 起草 | 人工填写与 AI 候选填表 | 字段准确率、人工修正量、完成时间、未确认写入次数 |
| 知识检索 | 既有四策略、相同语料和题集 | Recall@5、MRR、逐题证据与降级状态 |
| 落地边界 | 权限变化、错误输入、故障和数据变更 | 越权结果、无依据断言、误答/误拒答与正确降级 |

对照中保持数据范围、证据集合和任务一致，分别记录真实模型与模拟故障结果。报告绑定源码、数据集、提示词、工具配置及语料版本，并记录时延和 token；成本仅在有对应价格配置时计算。

有限回归集中“未观察到越权”不能写成绝对安全。模型自报置信度不能充当准确率。新增功能的题目与既有检索保留集分开管理，按场景家族划分开发与保留用例。

## 7. 推荐实施顺序与交付标准

1. 配置真实聊天服务，补齐新版本 fixture 与响应契约；冻结现有基线，改善最影响演示的路由、追问和实体消歧。
2. 完成订单页面上下文和有权限校验的证据读取，先让确定性检查能独立运行。
3. 加入真实模型解释、制度引用和保守降级，补齐审查场景评测；完成一条可现场演示的端到端任务。
4. 基于共用的实体解析与权限边界实现需求起草，验证未确认不写业务数据和已有编辑保护。
5. 形成对照报告、失败案例、运行配置和短演示。简历仅引用实际完成且可追溯的指标。

无凭据时可以完成接口、页面、确定性检查和模拟故障验证；真实模型效果与效率提升保持待验证。首版范围以完成一条稳定、可核对的业务任务为准。

推荐演示主线：“打开订单 → 询问需要核实的事项 → 查看数据与制度依据 → 切换受限角色 → 模型故障时查看真实检查结果 → 用自然语言准备申请并人工确认”。

最终可讲清的贡献是：发现跨页面查证和重复填表的成本，设计 AI 协助环节，通过受控服务集成、证据结构和人工确认将方案落地，再用任务级对照证明其价值。
